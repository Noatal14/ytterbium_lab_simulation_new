# Studies command catalog

For the project-wide dependency and data-flow map, see
`docs/ARCHITECTURE.md`.

`studies` exposes two canonical campaign managers at its root. Implementation
modules live in scientific-domain packages so that orchestration, workers,
validation tools, and historical evidence are not mixed in one flat directory.
Existing frozen campaigns remain reproducible from their pinned Git commits;
never combine a historical manifest or PBS file with a different checkout.

## Active 2D-MOT campaign

- `mot_2d_s0_campaign.py` — manifest-driven orchestration.
- `mot_2d/optimization.py` — screening/refinement worker.
- `mot_2d/production.py` — sealed production and uncertainty report.
- `mot_2d/validation/` — reusable 2D model checks.

## Inputs and reusable validation

- `zeeman/` contains corrected-ensemble generation, configuration checks,
  trajectory diagnostics, convergence tools, and the magnet-impact regression.
- `beam_source/` contains oven-flux and full thermal-source calculations.

## Active 3D-MOT campaign

`mot_3d_campaign.py` is the canonical manifest-driven manager. It generates the
PBS chains and calls stage-specific modules under `mot_3d/`:

- `discovery/` — optimization, merge, and candidate selection;
- `preliminary/` — independent early checks;
- `refinement/` — focused refinement and closure selection;
- `finalists/` — finalist selection and full-input evaluation;
- `analysis/` — shared retention metrics;
- `validation/` — reusable 3D model checks; and
- `integrity.py` and `final_validation.py` — provenance enforcement and sealed
  reporting.

The old standalone top-level helpers and submitters were retired. New code
should follow this stage hierarchy rather than adding another flat script.

New PBS files use the domain package paths generated by this manager. Old PBS
files must be run only from the old commit recorded in their manifest.

## Historical exploratory chains

The decisions from the donut-velocity/aperture and early single-pass scripts,
together with surviving evidence paths, are recorded in
`docs/3D_MOT_HISTORICAL_STUDIES.md`. These programs are not part of the active
campaign command surface.

## Application boundary

New UI code must use `workflow_api`, not import `submit_*` modules. The API is
side-effect-free: inspecting a campaign may produce a job plan, but it cannot
submit to Zeus. Scheduler submission will remain a separate, explicit user
action.

The current read-only boundary can also be inspected from the terminal:

```bash
python -m workflow_api list
python -m workflow_api inspect-2d path/to/campaign
python -m workflow_api inspect-3d path/to/campaign
```
